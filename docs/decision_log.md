# Decision log

Appended after every lab; becomes the Design Document on Day 6.

## L1 - Profiling
- **Limitations found:** no dates, no hospital id, heavy missingness (`medical_specialty` 49%, `payer_code` 40%, `weight` 97%), repeated patients (71,518 patients / 101,766 encounters). Each is carried into `data_contract.md` section 9.
- **Drop `weight`, `examide`, `citoglipton`.** Trade-off: losing a column versus keeping a 97%-empty one that invites false conclusions; constants carry no information.
- **Read with `keep_default_na=False`.** Default pandas turns the real `None` into 96,420 / 84,748 "missing" lab values; correctness over convenience.

## L2 - Contract and schema design
- **Simulated dates (seeded, sorted by encounter_id).** Trade-off: gives a time axis for trends, date-range queries and incremental loads, but every trend is illustrative; labelled in UI, API meta and docs. Alternative (no dates) would have dropped required features.
- **Race/gender only on `patients`.** Trade-off: one extra join to show them; in exchange a single place to hide from analysts and no repetition per visit.
- **Diagnoses and medications as child tables.** Trade-off: more joins than wide columns; removes repeating groups, and storing only prescribed drugs cuts 2.14M cells to 120k rows.
- **Lookup tables for admission/discharge/specialty/payer, ENUM for closed sets** (`readmitted`, `dosage_status`, lab results, roles). Trade-off: lookups need seeding and joins but carry descriptions and FK checks; ENUMs are compact but changing them needs a migration.
- **Outcome flags stored, not derived at query time.** Trade-off: redundancy (could drift from `readmitted`) versus a single writer, one definition of the eligible denominator, and indexable columns. A consistency test is added in L4/L5.
- **Soft delete (`is_deleted`) instead of hard delete.** Trade-off: every query must filter it (stated in the contract); preserves audit history and allows undo.
- **No FK on `dq_issues.encounter_id`.** Rejected rows never reach `encounters`; an FK would block recording them.
- **Rejected Claude-style review suggestions:** a hospital table (no hospital data exists); extra tables for age group and lab results (over-normalisation); storing `No` medication rows (94% noise).

## L17 - Scheduled pipelines (Airflow 3.1.8 in WSL2, APScheduler fallback)
- **Orchestration calls existing code; it does not contain it.** Every DAG task runs a script or `python -m etl.pipeline`; the logic (`etl.jobs`, `etl.pipeline`, `etl.reports`) is shared by Airflow, the fallback scheduler and the command line, so there is one implementation to test. DAG files import nothing from the project and make no database call at import, so they parse instantly (a test enforces it).
- **Airflow isolated in its own environment, on Linux.** Airflow does not run natively on Windows and its pinned dependencies conflict with FastAPI/Pydantic, so it lives in a virtualenv inside a user-level WSL2 Ubuntu (imported from a rootfs, no admin rights) installed with the official constraints file. Cost: two operating environments. The DAG tasks reach the project through WSL interop (Windows `python.exe`), so no project package is installed in the Airflow environment and MySQL stays on the Windows loopback.
- **Failure policy.** Retries 2 with a 2-minute delay (`HC_RETRY_DELAY_SECONDS` shortens it for demos); `on_failure_callback` writes one clear line; `catchup=False` (unpausing created exactly one run, not a backlog) and `max_active_runs=1` (two loads never overlap). Retries are safe because loading is idempotent (file hash + key checks); a deterministic failure (an over-threshold file) simply fails three times and stays visible.
- **Quality gate in its own task.** `check_quality` compares only the runs created after the marker the scan task produced (passed by XCom), fails on FAILED, RUNNING or non-reconciling runs and on a reject ratio above 5%, and treats "no new file" as a successful no-op. The 5% DAG limit is intentionally tighter than the pipeline's 20% hard stop: a file with 10% bad rows still loads its good rows, but operations are alerted. A task is red only on a non-zero exit, so the script is where a quality problem becomes a failure (tested).
- **Things found by running it, not by reading it:** (1) `airflow dags list` shows nothing until the DAG processor or `dags reserialize` has run; (2) `airflow standalone` starts components by name, so the virtualenv's `bin` must be on `PATH`; (3) an inline `PYTHONPATH=src` is not forwarded from WSL to a Windows `python.exe`, so modules run from `src/`; (4) background processes die when a `wsl` call returns, so long jobs run as foreground tasks; (5) unpausing an hourly DAG immediately runs the latest interval.
- **Fallback kept and verified.** `scripts/scheduler.py` (APScheduler) runs the same two jobs on the same schedules; honest trade-offs are in `docs/runbook.md` (no UI, simple retry loop, no catch-up). Airflow worked within the 60-minute budget, so the DAGs are the primary design.

## L14-L16 - React front end
- **Token storage: sessionStorage plus a single axios client.** The token survives a refresh but not a closed tab and is not shared across tabs; localStorage was rejected because it persists and is shared, which widens the exposure if a script ever ran in the page. The app never renders untrusted HTML and the token is never placed in a URL (downloads use an authenticated request and a blob, not `window.open`). The role always comes from `GET /auth/me`, never from storage. Cost: the user signs in again per tab.
- **Proxy instead of CORS in development.** Vite forwards `/api` to FastAPI, so the browser sees one origin; the API's CORS list (`http://localhost:5173`, `http://127.0.0.1:5173`) is the fallback if `VITE_API_BASE_URL` points straight at the API. Vite is bound to `127.0.0.1` because Node 24 resolves `localhost` to IPv6 only.
- **Route guards are UX only.** `ProtectedRoute` and `RoleRoute` keep people out of pages they cannot use; every action is still checked by the API. A real-browser run compares what the UI shows with what the API answers for the same call, per role (`docs/role_verification.md`: all agree).
- **No rate is ever computed in the browser.** The dashboard formats numbers from the API and nothing else; the one derived value (the overall length-of-stay histogram) was moved into the API as `group_by=overall` rather than summing groups in the client.
- **Stale requests.** `useApi` aborts the previous request and ignores late responses; a unit test resolves the old response last and checks it cannot overwrite the new data, and the browser run changes the filter six times in half a second and checks the page matches the API for the last selection.
- **State in the URL.** List pages (patients, encounters, audit, pipeline, data quality, history) keep filters, sort and page in the query string, so a filtered view can be shared or bookmarked and survives a refresh; paging, sorting and filtering are always server-side.
- **Forms mirror the API.** Client rules reuse the same limits as the ETL and API (length of stay 1-14, dates must agree, ICD-9 pattern, count caps) so most mistakes never leave the browser; any rule the client misses comes back as a 422 and is shown against the right field. Derived flags are displayed, never sent.
- **Found by looking at the screenshots, not by tests:** long category names overlapped on the horizontal bar chart and the x-axis labels ran together; fixed by truncating axis labels (full text stays in the tooltip) and angling them. Two server-behaviour surprises from the real-browser run: leftover test records from a crashed run (cleaned up; runs now use unique ids) and the IPv6 binding above.

## L12 - Indexes and query optimisation (evidence: docs/performance_notes.md)
- **Measure first, on realistic volume.** A scratch database holds all 101,766 encounters plus 300,000 synthetic audit rows; every query was run 6 times (first discarded, median of 5) with EXPLAIN and EXPLAIN ANALYZE before and after. Result: four indexes kept, each named by its plan and each shown to slow the query again when dropped (Q1 1.3 ms -> 31 ms, Q6 9 ms -> 51 ms, audit queries from 65-86 ms to under 2 ms).
- **One proposed index rejected on evidence.** `audit_logs (username, created_at)` looked right on paper but dropping it left the query at 1.4 ms (the `created_at` index already narrows to ~20,000 rows), so it was removed from the models and `indexes.sql`. An index that cannot be shown to help only costs writes.
- **The real problem was the view, not the indexes.** The view joined `patients` only to hide soft-deleted patients; the optimizer then started from a scan of `patients` and probed `encounters` once per patient, and the plan flipped from fast to slow when statistics were refreshed. Histograms and an index on `patients.is_deleted` did not fix it; rewriting the check as `NOT EXISTS` did (same rows, scan starts at `encounters`; Q6 765 -> 68 ms before any index). Trade-off: the view is slightly harder to read; behaviour is pinned by the soft-delete tests.
- **Pre-aggregated summary table: rejected for now.** Q4 and Q7 still take 0.6-0.8 s because they must read every encounter through an eight-table view; even a hand-built lean query took ~300 ms. A summary table would make them instant but must be refreshed after every load and every write (staleness, an extra step, extra tests) to save about half a second on dashboard calls that run in parallel. Revisit at roughly 10x the data.
- **Write cost recorded:** loading all five batches takes 22.2 s without and 23.8 s with the indexes (+7%).
- **Lesson:** a failed `apply_views` hid behind `2>$null` and produced a false "view only" result; I now run steps with errors visible and check the deployed view before trusting a measurement. A PowerShell edit also wrote a UTF-8 byte-order mark into `views.sql`; the SQL readers now use `utf-8-sig`.

## L13 - Reports and exports
- **One generator for API and scheduler.** `etl/reports.py` has no web types: `build_report` (bytes), `record_run`, and `generate_report` (commits; takes `triggered_by`, optional `save_dir`). The API composes build + record + audit in one transaction; the scheduler calls `generate_report` directly. It reuses `app.services.analytics`, so report totals equal the dashboard by construction (and tests prove it).
- **Exports are a data-leak path.** The encounter-level report uses an explicit column allow-list (no race, gender, or source batch) and a test searches both header and values; it is restricted to administrator and clinical_ops, capped at 50,000 rows (413 with an actionable message, before any file is built), and every export writes a `report_runs` row plus, for encounter-level files, an `EXPORT` audit row in the same transaction. A forced audit failure leaves no `report_runs` row.
- **CSV is header + data only** (aggregated reports are long-format with a `breakdown` column); context lives in the Excel Metadata sheet and the file name, so imports into other tools never break.
- **Excel:** Summary, one sheet per breakdown, Metadata (generated_at, filters, row count, the simulated-dates statement, the denominator and definitions). Real numbers, real dates, percent-formatted rates, styled header, column widths.
- **Cap rationale:** an Excel workbook of 100,000 rows x 29 columns is built in memory and can exhaust memory and time out; 50,000 rows measured at about 1.4 MB for 10,796 rows, so the cap keeps requests in seconds.

## L9 - CRUD with validation and audit
- **Audit inside the data transaction.** `audit.record` only adds a row to the session; the service commits once. A crash or error between the change and its trail is impossible: tests force a failing audit write and a failing commit and show that neither the data nor an audit row remains (create, update, delete). Trade-off: every write path must remember to call `record` (enforced by tests per endpoint), and an audit failure blocks the business change.
- **Soft delete, one read path.** Reads go through `v_active_encounters`; writes check the encounter and its patient are active. Hard delete was rejected because audit and undo need the row, and because analytics must be able to exclude (not lose) data. Cost: every query must use the view; a test fails if a KPI query touches the base tables.
- **Server-derived flags.** `readmitted_30d`, `any_readmission` and `is_readmission_eligible` are computed from `readmitted` and the disposition on every create and update; client values are ignored (extra fields are dropped, tested). One bad request can therefore never skew a readmission statistic.
- **Validation is shared with the ETL.** The numeric caps, ICD-9 pattern, study window and "dates must agree with length of stay" come from `etl.quality` / `etl.transform`, so a record is accepted by the API exactly when the pipeline would accept it. Cross-field checks live in the service, not in Pydantic model validators, because Pydantic reports model-level errors at `loc: ["body"]` and the contract wants field-level messages.
- **Data minimisation by role through one schema.** `EncounterOut` leaves `patient_nbr` and `source_batch_id` unset for analysts and responses use `exclude_unset`, so the keys are absent rather than null; race and gender exist only on `/patients` (403 for analysts). Analysts also cannot filter by `patient_nbr` (403), which would re-identify rows, and numeric `q` only matches `encounter_id` for them.
- **409 versus 422 for missing parents.** Duplicate keys are 409; an unknown patient or lookup id inside a valid-looking body is a field-level 422, because the request is wrong rather than in conflict.
- **Audit snapshots exclude timestamps** so before/after differ only where the data changed (checked: an update row differs in exactly `readmitted`, the derived flags and `number_inpatient`).

## L10 - Filtering, sorting, pagination, search
- **Whitelist plus tiebreaker.** `sort_by` is a `Literal` (so FastAPI answers 422) and `apply_sort` looks the name up in a dict of column objects; the primary key is appended in the same direction. Verified by walking all pages with page_size 7 on every sort column and direction: every row exactly once, in the oracle order, despite heavy ties.
- **Search semantics:** digits only = exact id; everything else = ICD-9 prefix (`LIKE prefix%`, wildcards escaped, never a leading wildcard, so the index on `icd9_code` can be used). Trade-off: you cannot search ICD prefix `250` without a dot; documented in `docs/api_parameters.md`.
- **Date filters on DATE columns** (`<= date_to`), and on DATETIME columns (audit, runs) `< date_to + 1 day`, so the last day is included.
- **Count query next to the data query** on the same filtered statement (no OFFSET beyond the end, a page past the last returns an empty list and the true total). Cost: two queries per list; acceptable at this size and measured in L12.
- **Same envelope everywhere**, with the applied filters echoed in `meta` for debugging. Admin and reference endpoints reuse the helpers.

## L11 - Analytics
- **Aggregation in SQL, rates in Python.** Counts and averages come from `func`/`case` over the view; the rate is `round(readmitted_30d / eligible, 6)` from the integer counts, avoiding MySQL's 4-decimal division. A rate with no eligible encounters is `null`, never 0.
- **One definition.** The numerator/denominator expressions mirror `db/queries/kpi_queries.sql`; tests assert `/analytics/summary` equals the L7 headline SQL, and `verify_kpis.py` now also checks the API against pandas on the real data (88 of 88).
- **No fan-out.** Group queries never join diagnoses; the drug query joins `encounter_medications`, whose key is (encounter, drug). Tests and a live run assert that group counts add up to the filtered total for every `group_by`.
- **Privacy:** no race or gender anywhere; groups under 11 encounters carry `small_n`; every response says `dates_simulated: true` and states the denominator in words; months without encounters are omitted.

## L6 - Load, incremental processing, run logging
- **Incremental strategy: file hash plus key check; no date watermark.** The SHA-256 of a file stops the same bytes being processed twice; the pre-selected `encounter_id` check stops the same rows arriving in a different file (shown by the reordered-copy run: 5,089 rows, 0 loaded). A watermark ("only rows newer than the last admission_date") was rejected because late-arriving rows would be lost forever. Trade-off: the key check costs one indexed lookup per chunk of ids.
- **One transaction per file, chunking only for statement size.** A crash on chunk 9 must not leave 8 chunks behind (the rerun would then skip them as existing and the file would stay half-loaded without any error). Verified by a test that forces a failure after encounters were inserted: zero rows remain and the same file loads afterwards.
- **No INSERT IGNORE.** It silently discards rows that violate keys or exceed column sizes, so counts look right while data is wrong. Existing keys are pre-filtered and real errors raise.
- **Run record is written outside the load transaction** so a failed load still leaves a FAILED row with the message; only a SUCCESS run blocks a hash, so failed files can be retried.
- **Reconciliation enforced in code, inside the load transaction:** a mismatch rolls the load back. For a file refused at the 20% threshold every row counts as rejected so the run still reconciles; the real number of rule failures is kept in the summary.
- **Patients: insert new, fill NULL race/gender on existing, never overwrite non-null.** Trade-off: a corrected race in a later file is ignored; the rule protects data that was already trusted.
- **Reference ids come from the database**, not the file, so the pipeline and the API agree on what is valid and an unseeded database fails clearly (`ReferenceDataError`).

- **Found by a real hard-kill test (process killed while its open transaction held 103,861 modified rows):** (1) the database kept none of the killed file's rows, and retrying the same file loaded all 81,412; (2) the killed run stayed `RUNNING` forever, so the next attempt for the same file now closes any older `RUNNING` run with that hash as `FAILED` ("Interrupted ...") and leaves other files' runs alone; (3) the CLI never wrote a log file because it configured a logger named `pipeline` while the modules log as `etl.*`, and `pipeline.py` itself logged as `__main__` under `python -m`; both fixed (logger `etl`, file `logs/etl.log`) with a regression test. Lesson: tests that pass on in-process calls do not prove the command-line path works; the log file must be read, not assumed.

## L7 - KPI queries and views
- **One view as the single filter point.** `v_active_encounters` excludes soft-deleted encounters and encounters of soft-deleted patients and omits race/gender; every KPI, and later every API list, reads from it. Verified by tests: soft-deleting one encounter lowers the headline count by exactly one; deleting a patient hides all their encounters; a source check asserts no query reads `encounters`/`patients` directly.
- **Eligible denominator through conditional aggregation.** Counts and average LOS use all active encounters; the rate is `SUM(eligible AND readmitted_30d) / SUM(eligible)`. A rate over all encounters would read 0.111548 instead of 0.114258 and raise no error.
- **Verified against a second implementation.** `scripts/verify_kpis.py` recomputes in pandas from the raw CSV; 59 of 59 checks pass.
- **Precision:** MySQL division keeps only 4 decimals, so rates are computed as `1.000000 * numerator / denominator` and rounded to 6 decimals.
- **Moving average** is the mean of the current and two previous monthly rates (window function), not a pooled rate; the definition is in the contract.

## L8 - FastAPI foundation
- **Token design:** HS256 JWT with only `sub`, `role`, `iat`, `exp`; 60-minute lifetime (short enough that a stolen token expires, long enough for a demo session). No refresh tokens: trade-off is re-login each hour, in exchange for no server-side token store.
- **Roles are enforced in one place (`deps.require_roles`) driven by one constant (`permissions.PERMISSIONS`).** The role is read from the database on every request, so deactivating a user or changing a role takes effect immediately and a forged role claim is useless (tested). A test parses `docs/data_contract.md` and fails if the document and the constant disagree.
- **Uniform error contract** for 401/403/404/405/422/500 via one set of handlers; 422 details drop the submitted input (a mistyped password must never be echoed); database and unhandled errors return generic messages and are logged with the request id.
- **One message for unknown user, wrong password and inactive user,** and a dummy bcrypt check for unknown users so timing does not reveal valid usernames.
- **bcrypt used directly (no passlib)** to avoid the known import failures with recent bcrypt releases.
- **Startup refuses a missing, short (< 32) or placeholder `JWT_SECRET`.**
- **Request id** generated per request, returned in `X-Request-ID` and attached to every log line through a contextvar.
- **Testing note:** FastAPI 0.143 keeps included routers lazy (`app.routes` no longer lists endpoints), so the "every route needs a token" test enumerates endpoints from the OpenAPI spec; it was mutation-checked (an unprotected route is flagged).

## L3 - Schema, models, seeding
- **Source keys, no AUTO_INCREMENT** on `encounter_id` / `patient_nbr`. Trade-off: the loader must supply keys, but reloads never renumber data and duplicate detection stays meaningful. Verified in `SHOW CREATE TABLE` and a test.
- **Cascade rules.** Child clinical rows (`encounter_outcomes`, `encounter_diagnoses`, `encounter_medications`) cascade from `encounters`; everything else is `RESTRICT` (lookups, `patients`, `medications`); `audit_logs.user_id` is `SET NULL` so deleting a user never deletes history; `dq_issues` cascades from `pipeline_runs`. Trade-off: cascades make a hard delete of an encounter clean, but routine deletion is soft anyway.
- **Why the DDL is exported.** `db/schema.sql` lets a reviewer build the database without Python (verified by loading it into an empty database: 16 tables). It is generated from the models, never hand-edited, so the two cannot drift.
- **Users seeded without committed passwords.** Passwords come from environment variables or are generated once and printed; only bcrypt hashes are stored. Existing users are never modified (re-running is safe). Cost: a generated password is shown only once.
- **Tests run on `healthcare_test` only.** The fixture refuses any database whose name is not a `*_test` schema and not equal to the development database, so cleanup can never wipe loaded data.
- **Pipeline status values** extended to `RUNNING, SUCCESS, FAILED, SKIPPED_DUPLICATE_FILE` (as the L6 prompt requires) instead of a free-text column.

## L4 - Extract and transform
- **Pure functions, no I/O in `transform.py`.** Trade-off: the loader must do the writing, but every rule is unit-testable on a 30-row fixture and the same functions can run unchanged from Airflow.
- **"No" medications are not stored.** Measured on the initial batch: 95,251 prescribed cells instead of about 1.6M mostly-"No" rows (81,412 x 21 drugs); the count of non-"No" raw cells equals the rows built.
- **Simulated dates: seed 42, sorted then assigned in encounter order.** Sorting preserves the link between encounter order and time so incremental batches do not overlap in date (initial batch 1999-01-01..2007-03-19; batches 001-004 follow in order). Acceptable because dates only exist to drive trend and incremental mechanics; never a clinical claim.
- **Missing-value report is taken before dropping columns**, so `weight`'s 96.9% missingness stays documented.
- **Patient race/gender = first non-null by lowest `encounter_id`.** Trade-off: arbitrary but deterministic and matches DQ13's "keep first non-null".
- **Environment note:** the venv resolved pandas 3.0.6. All code and tests pass on it; one pandas-3 behaviour (`astype(str)` keeps NaN) caused a real bug in DQ01's detail text, fixed in `_first_failing`.

## L5 - Data-quality rules
- **Reject / correct / flag / measure.** Reject what would break keys or analytics (DQ01-05, 07-10); correct what can be nulled without losing the row (DQ06 ICD format); flag what is suspicious but legitimate (DQ12, DQ13); measure missingness (DQ11). Trade-off: strictness versus data loss - every rejected row costs a real encounter, so only rows that cannot be trusted are rejected.
- **DQ06 accepts short numeric codes.** A strict 3-digit rule would have corrected 5,732 genuine codes (the source dropped leading zeros). Found by testing the rule on real data before trusting it.
- **DQ08 allows discharge up to 14 days after the window end**, otherwise genuine stays that begin in late December 2008 would be rejected.
- **DQ10 only runs on otherwise-valid rows**, so a single injected fault produces one rule hit, not two; the faulty-batch test can assert exact counts.
- **File-level threshold 20% (`MAX_REJECT_RATIO`).** A file that is mostly bad is more likely a wrong file or a broken export than a few dirty rows, so it fails whole and loads nothing; below the threshold good rows load and bad rows are quarantined with a reason. Trade-off: a genuinely dirty but important file will be refused until it is fixed or the threshold is raised deliberately.
- **Rejected rows are quarantined, not dropped** (`data/rejected/*.csv` with `rule_name` and `reason`); `dq_issues` keeps at most 500 examples per rule, the true counts live in the run summary.

## L0 - Environment and repository
- **Python 3.12 locally (guide suggests 3.11).** Trade-off: 3.12 works for everything built so far (pandas 2.2, SQLAlchemy 2.0); Airflow wheels lag newer Pythons, so Airflow gets its own virtualenv (and WSL2 if needed) in L17, keeping the project venv free of it.
- **MySQL 8 with a least-privilege user `hc_app`.** The app can only touch `healthcare_db` and `healthcare_test`; a bug or leaked credential cannot reach other databases. Cost: one extra setup step (`db/setup_database.sql`).
- **`src/` as the Python root.** Imports read `app.models`, `etl.transform`; tests and scripts add `src` to the path (`pytest.ini: pythonpath = src`). Avoids path hacks and mirrors how packaged code is laid out.
- **`.env` git-ignored, `.env.example` committed.** Secrets never enter history; reviewers still see which settings exist.
